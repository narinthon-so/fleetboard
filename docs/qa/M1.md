## Defect Summary

Four defects were identified during test execution:

### 1. CardDetail crashes React (Minified React error #31) when rendering tasks with dependencies
- **Severity**: Major (Severity 1)
- **Component**: `web/src/components/CardDetail.tsx`, `web/src/types/api.ts`, `src/server/api.rs`
- **Steps to reproduce**:
  1. Create two tasks: `fb add "Task A"` (`fb-1`) and `fb add "Task B"` (`fb-2`).
  2. Add dependency: `fb dep add fb-2 fb-1`.
  3. Start `fb serve`, log in to the web UI, and open `fb-2` (click card or navigate to `/task/fb-2`).
- **Expected**: Detail sheet renders successfully, showing `fb-1` under "Blocked By" in the Overview tab.
- **Actual**: React crashes with uncaught error: `Minified React error #31: Objects are not valid as a React child (found: object with keys {id, status, title}). If you meant to render a collection of children, use an array instead.` The detail sheet displays a blank white error state.
- **Root Cause**: `src/server/api.rs` (lines 217–221) serializes `blocked_by` as `Vec<{id, status, title}>`, whereas `web/src/types/api.ts` defines `blocked_by: string[]`. In `CardDetail.tsx` (lines 584–593), `{task.blocked_by.map((depId) => <button key={depId}>{depId}</button>)}` attempts to render the `{id, status, title}` object directly as a React child. Additionally, `allTasks.filter(t => t.blocked_by.includes(taskId))` in `CardDetail.tsx` fails to match blocking tasks, and `BoardView.tsx` toast displays `([object Object])`.
- **Impact**: Any task with dependencies crashes the web UI detail view when opened by a user.

### 2. Duplicate doc comment on `fb serve` repeats command description in help text
- **Severity**: Minor (Severity 2)
- **Component**: `src/cli.rs`
- **Steps to reproduce**:
  1. Run `fb serve --help`.
- **Expected**: Help text displays: `Start the loopback HTTP server and web UI`.
- **Actual**: Help text displays: `Start the loopback HTTP server and web UI Start the loopback HTTP server and web UI` (description repeated twice).
- **Root Cause**: Consecutive identical doc comments in `src/cli.rs` (lines 184–185).
- **Impact**: Cosmetic duplication in CLI help output.

### 3. Global keyboard shortcut `Enter` does not open selected board card
- **Severity**: Minor (Severity 2)
- **Component**: `web/src/App.tsx`
- **Steps to reproduce**:
  1. Use `j`/`k` to select a task card on the board.
  2. Press `Enter`.
- **Expected**: Detail sheet opens for the selected card per `docs/ui.md` line 125 and `ShortcutsDialog.tsx` line 15.
- **Actual**: Nothing happens. The event handler in `web/src/App.tsx` (lines 291–296) contains an empty stub comment (`// Card is open or selected`).
- **Impact**: Keyboard-only board navigation is incomplete; users must click or press another key combination to open cards.

### 4. Web UI requires force confirmation dialog to verify note tasks without commits
- **Severity**: Minor (Severity 2)
- **Component**: `web/src/components/CardDetail.tsx` (line 123), `web/src/components/BoardView.tsx` (line 246)
- **Steps to reproduce**:
  1. Create a note task: `fb add "Audit Note" --kind note`.
  2. Claim and complete: `fb claim fb-1 && fb done fb-1 --result "Completed note"`.
  3. In web UI, click Verify on the card or drag to Done.
- **Expected**: Per `IDEA.md` D4 ("For note, the task closes on a written result with no git check"), note tasks close on result without commit evidence and do not prompt for force confirmation. The backend API permits verifying note tasks without force.
- **Actual**: The web UI checks `task.evidence && task.evidence.commits > 0` without checking `task.kind !== 'note'`, triggering the warning modal: "Verify without evidence: verify with --force?".
- **Impact**: Unnecessary confirmation friction when verifying valid note tasks in the browser.
